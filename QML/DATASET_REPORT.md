# Dataset Report

This project uses a **single dataset: the Z24 Bridge benchmark** (progressive
damage test). This report is the auditable provenance record. Machine-readable
checksums, array shapes, and label distributions are generated by the
acquisition script and stored at
[`reports/provenance/z24_provenance.json`](reports/provenance/z24_provenance.json)
— this document never hand-copies numbers that the script can verify.

> **Integrity policy.** No dataset contents, metrics, or results are fabricated.
> All facts below were verified from the source dataset card on **2026-06-19**;
> the provenance JSON is regenerated on every download.

---

## 1. What it is

The **Z24 Bridge** was a post-tensioned concrete highway bridge near Koppigen,
Switzerland, instrumented and then subjected to a controlled **progressive
damage test (PDT)** before demolition (full-scale monitoring campaign led by
KU Leuven / EMPA). It is one of the field's canonical vibration-based SHM
benchmarks. The PDT introduced a sequence of realistic damage scenarios
(e.g., pier settlement, concrete spalling, tendon/anchor failures).

## 4. Files & structure

| File | Description |
|---|---|
| `inputs.npy` | Acceleration windows, shape **(1530, 27, 6000)** = (windows, sensors, timepoints) |
| `labels.npy` | Integer damage-state label per window |
| `data_visualization.ipynb` | Mirror author's exploration notebook (reference only) |

- **27 sensors**: accelerometers at bridge locations.
- **1530 windows**: 17 scenarios × 9 setups × 10 segments, 6000-point windows.
- **Confirmed (2026-06-19):** `inputs.npy` float32 (1530, 27, 6000); `labels.npy`
  int64 (1530,) with **17 classes (0–16), exactly 90 windows each** (balanced).
- Full dtypes/checksums/per-class counts: see the provenance JSON.

**Unsupervised use of a labelled set.** Although labels exist, Q-GUARD trains on
the **healthy/reference class only** (label `0`, pending reconciliation with
Reynders et al. 2008); all other classes are revealed **only to the evaluator**.
The balanced 17-class layout is convenient for ROC/PR analysis but is never used
to supervise the detector.

## 5. Processing already applied by the mirror

Per the dataset card, the raw data (17 scenarios × 9 setups × 27 sensors ×
65,530 timepoints) was: quality-controlled (corrupted points removed),
normalized to 60,000 samples, then segmented into 1,530 windows of 6,000
timepoints. **Implication:** our own preprocessing (M3) must not double-apply
normalization; we treat these as cleaned raw windows and document any further
transforms.

## 6. Known caveats / open risks

1. **Temperature record CONFIRMED ABSENT (2026-06-19).** Inspection of
   `labels.npy` shows a plain 17-class integer array with **no temperature or
   environmental channel**. Z24's famous ~1-year environmental series is not in
   this mirror. **Decision (D33):** the environmental-confound study (**M11 /
   E04**) is reframed as a **controlled synthetic-confound proof-of-concept** —
   we inject a temperature-like global modulation into the healthy windows and
   show the tangent-space projection rejects it without losing damage
   sensitivity. This is **clearly labelled as synthetic** in all reporting; we do
   not claim a real-temperature result. Sourcing the real long-term data from
   KU Leuven remains an optional future extension.
2. **Third-party processing.** Segmentation/normalization choices are the
   mirror author's; raw KU Leuven histories differ. We rely on the mirror's
   structure but document it as such.
3. **Label semantics (RESOLVED, D34).** The mirror does not publish the
   integer→scenario map. `loaders/z24.py:Z24_SCENARIO_NAMES` encodes the canonical
   Z24 PDT order (Reynders et al. 2008) as a *documented assumption*; healthy =
   label `0`. Alignment is to be empirically validated in M4 EDA (healthy class
   should form the tightest feature cluster); the healthy label set is
   configurable so no result hard-depends on this assumption.
